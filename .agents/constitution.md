# Protube Constitution

Verifiable principles for specifications, plans, implementation, and review.
User instructions and applicable `AGENTS.md` rules remain in effect.

1. **Understand and keep things simple.** Inspect code, tests, dependencies, and configuration before making changes. Keep the existing Java 21/Spring Boot/Maven, React/TypeScript/Vite, and Python tooling; reuse patterns and justify new dependencies. Do not invent existing functionality or introduce refactoring outside the scope.
2. **Specify before implementing.** Every behavior change must have observable requirements in its spec, a design in its plan, and verifiable tasks, following [SDD](../docs/SDD.md). Update these before changing the contract, without altering acceptance criteria to hide failures. Respect the authorized phase; resolve blocking questions and document routine assumptions. Documentation, formatting, and test coverage of existing behavior do not require a fictitious spec.
3. **Separate responsibilities.** Backend: Controller -> Service -> Repository, HTTP validation in controllers, business logic in services, and public DTOs without persistence entities. Frontend: presentation components and data access through reusable hooks or clients. Keep logic testable through focused tests.
4. **Verify with evidence.** Cover success, invalid input, empty results, and relevant errors; include loading states and accessible UI queries where applicable. Mock API boundaries in frontend tests. Run the area checks defined in its `AGENTS.md`; do not mark tasks complete when required checks have failed or remain pending. Declare failures and tests not run; read-only reviews report findings without editing files.
5. **Protect data and existing work.** Use persistence and services according to the project's actual configuration and profiles, without imposing the example's local JSON storage. Supply secrets through the environment; configure the external media store through `ENV_PROTUBE_STORE_DIR` and `pro_tube.store.dir`, validating paths against the store. Do not commit credentials, media, local paths, or generated artifacts. Preserve others' changes, including uncommitted work.
6. **Maintain traceability and collaboration.** Link requirements, tasks, and verification; preserve prompts with their actual approval status. Use shared skills without duplicating rules per provider. Follow `feature/<ticket>-short-name` branches, Conventional Commits, and reviewed PRs with squash merges; never push directly to `main`. Preserve existing language conventions without translating code or messages outside the scope. Do not invent approvals or results.
